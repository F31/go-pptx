# go-pptx v1.0 Bug Registry（已知小问题登记）

> 建立日期：2026-09-12（v1.0.2 patch release 后；本文件落地即 1.x 路线图阶段 1 的 **C-3 已知小 bug 修复登记**）
> 维护者：所有 v1.x 维护者在识别到小问题时增补条目
> 关联文档：[`1.x-roadmap.md`](1.x-roadmap.md) · [`coverage-roadmap.md`](coverage-roadmap.md) · [`v1.0-freeze-list.md`](v1.0-freeze-list.md) · [`client-compat-matrix.md`](client-compat-matrix.md) · [`RELEASE-NOTES-v1.0.2.md`](RELEASE-NOTES-v1.0.2.md)

## 目的

把"v1.0 期间识别的小问题（如 ifAny 残留、warning 文本不当）"按四类归档化——

1. **已修历史**：滚动归档（含 commit 链接），避免 1.x 期间被再次发现而重复修
2. **已决策放弃**：不算 bug，按 ADR / 路线图决策归档（口径、不追的覆盖率项）
3. **已知限制**：V1 不承诺 / 设计态（让"我有这个限制"成为公开承诺而非隐藏缺陷）
4. **移交 1.x**：路线图 backlog 中的待办，按工作量排期

新增问题按"是否阻塞 patch / minor release"分流：

- 阻塞 → §1 立即修
- 不阻塞但有价值 → §4 排期
- 设计态 / 决策放弃 → §2 归档
- 用户能感知到的限制 → §3 公开承诺

每次 patch / minor release 时：§1 段末追加该 release 期间修复的 commit 列表。

## §5 维护流程

1. **发现小问题**：先 `git grep -E '(TODO|FIXME|XXX|HACK)'` 确认仓库现状；如确实未登记，按 §0 分流落档
2. **新加条目**：在对应段加一行（保留表格格式）；§1 加 commit 链接；§4 加工作量估计
3. **patch release 时**：§1 段末加该 release 修复 commit 表
4. **minor release 时**：重审 §3 / §4，根据新增能力把"已知限制"移走 / 把"移交 1.x"标 ✅
5. **major release 时**：清空 §1（归档到 release notes），重写 §3 / §4
