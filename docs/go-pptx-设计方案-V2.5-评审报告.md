# go-pptx 组件设计方案 V2.5 评审报告

> 评审对象：`go-pptx_完整设计方案_V2_5_开发实施版.md`
> 评审维度：逻辑合理性、架构先进性、产品创新性、功能完整性
> 结论：**这是一份工程成熟度很高的文档**，四层校验、词法保真存储、revision事务模型、能力矩阵、ADR决策记录、验收用例、工作包拆分，已经达到"可以直接开工"的严谨程度，明显优于此前V1/V2.1/V2.2的探索性方案。本次评审不再纠结"方向对不对"，而是在这个高基线上找**四类真实的、有具体证据支撑的优化点**，不做低价值的重复确认。

---

## 〇、总体评价

这份文档相比此前版本有质的提升，几个地方尤其值得肯定：

- **词法保真的工程化程度**：4.3节的XML存储层设计（节点跨度、命名空间作用域、`mc:AlternateContent`分支处理）已经不是"原则声明"，而是给出了具体的数据结构（18.1节`NodeRecord`/`ByteRange`），这是此前V2.1/V2.2停留在"原样透传字节"这一句话原则上没有做到的深度。
- **诚实的能力分级**：B0/B1/S1/V1/P1五级保真等级，以及"Inspect/Create/Edit/Preserve/Render/Play"六维能力状态，把"这个功能到底做到什么程度"这件事从模糊的文字描述变成了可测试、可发布的结构化声明，这是全文最大的亮点之一。
- **立项纪律**：2.4节"任何新能力必须强化下述叙事主线之一，否则不立项"，以及ADR 012/013/014里对"为什么不做动画编辑""为什么不做像素级渲染"给出的明确取舍理由，避免了功能蔓延。

在这个基础上，以下按四个维度给出具体发现。

---

## 一、逻辑合理性

### 1.1 【一致性良好，无需修订的确认项】
- SmartArt/OLE/动画的"P档透传"策略与AT-01验收用例、2.2边界表、13章安全策略（不执行OLE/脚本）三处描述完全自洽，没有发现矛盾。
- 21.5节动画时序IR明确声明"时序IR的估计值不得作为AdvanceAfter的计算输入"，这是一处主动预防"新功能悄悄污染旧模块承诺"的设计，值得肯定，说明团队对"创新扩展不能反向拉低核心承诺"这条纪律执行得很到位。

### 1.2 【发现问题】能力矩阵（2.3）与工作包backlog（24章）之间缺乏可追溯映射

这是本次评审发现的**唯一一处实质性逻辑缺口**。2.3节的能力矩阵为约30项特性逐一声明了目标档位和目标阶段（M0-M6），但24章的工作包列表只覆盖了其中一部分，以下M6目标特性在24章找不到对应工作包：

| 矩阵中声明M6交付的特性 | 24章是否有对应工作包 |
|---|---|
| 章节/自定义放映（R） | 否 |
| 嵌入字体识别（R） | 否 |
| 讲义母版/视图属性（R） | 否 |
| 避头尾规则（R） | 否 |
| 视频媒体形状（E） | 否（MEDIA-01只提到MP3/WAV probe，未提视频） |
| 自定义几何`custGeom`（R） | 否 |
| 效果模型`effectLst`（R） | 否 |
| 渐变/图案填充（R/E） | 否 |
| 线条系统`a:ln`（E，目标M3） | 否（可能隐含在GEOM-01或STYLE-01，但未点名） |
| 文本框高级项`numCol`/`vert`（R/E） | 否 |
| 字段全集`a:fld`逐类型（E） | 否 |
| 图表标签/误差线/趋势线/轴扩展（R） | 否 |
| 过渡动画`p:transition`（R/E基础） | 否 |
| 主题样式矩阵`styleMatrixReference`（R，目标M3） | 否（STYLE-01描述是"基础占位符和样式解析"，未点名样式矩阵） |
| 颜色变换全集（R，目标M3起） | 否（同上，STYLE-01未点名） |

**这不是"文档不完整"层面的小问题，而是逻辑闭环上的一个洞**：16章的M3/M6阶段描述本身就写得很笼统（"M6扩展阶段｜跨文档合并、Strict、更多客户端、渲染适配｜单独估算"），既然2.3节已经把M6拆解到了如此精确的特性粒度，24章backlog和16章milestone描述理应同等精确地承接这份清单，否则2.3矩阵存在"精确声明了目标，却没有落实到可执行任务"的风险——这份矩阵在实际排期时很容易变成一份"看起来很完整、实际没人认领"的文档。

**建议**：要么在24章为上述每一项补充对应工作包（哪怕标注"M6单独排期，暂不分解到子任务"这种占位状态也比完全缺失要好），要么在2.3节矩阵末尾显式加一句"本矩阵M6档位特性的工作包分解将在M5验收后补充，当前不作为M0-M5范围的完成度依据"，把"矩阵存在但backlog未覆盖"这件事本身写成一条明确声明，而不是留白让人误以为遗漏。

### 1.3 【发现问题】"文档不表示功能已实现"的免责声明与验收门槛章节的详尽程度形成一定张力

文档开头声明"本文定义目标架构、开发契约与验收要求，不表示相关功能已经实现或完成兼容测试"，这条声明本身没问题，但15.3节发布硬门槛、25章验收用例都写得极其具体（比如AT-06给出了精确的10s/8s/6s数字），这种精确度容易让读者（尤其是非技术决策者）产生"这些数字已经被验证过"的错觉。

**建议**：在15章开头补一句类似"以下验收用例是测试设计规格，用于指导测试用例编写，不代表已执行并通过"，把"设计态"和"验证态"的区分再往前提一层，避免文档内部不同章节的"确定性语气"产生落差。

## 二、架构先进性

### 2.1 【已经做得好，无需重复肯定的部分】
revision-based乐观并发控制（SavePlan.BaseRevision + ErrConcurrentModification）、原子保存（临时文件+rename+失败恢复）、资源预算体系（13章）、四层校验——这套组合放在同类PPT库里已经是相当先进的工程设计，比V2.1停留在"分层+接口"的讨论层面要扎实得多。

### 2.2 【发现机会】纯Go+CGO_ENABLED=0的架构红利没有被充分兑现：WASM可编译性

文档反复强调"纯Go、CGO_ENABLED=0、无外部运行时强依赖"（1.2节、26章），但**全文没有任何地方提到WASM编译目标**。这是一个几乎零成本、但在架构先进性上很有说服力的验证点：一个真正"纯Go、零cgo"的库，天然可以`GOOS=js GOARCH=wasm`编译，这个能力在office_oxide（Rust核心+WASM壳，有额外桥接开销）和python-pptx（完全无法在浏览器运行）身上都做不到。

**建议**：在26章"工具链、依赖与发布管理"里加一条CI验证项——"每次发布验证`GOOS=js GOARCH=wasm`能否成功编译核心包"，这不需要额外开发工作量（如果真的零cgo，这个验证大概率直接通过），却能把"纯Go"这个已经声明的架构约束，转化成一个可以写进发布物料、有实际差异化意义的能力证明。这也为下一节的产品创新建议打了地基。

### 2.3 【发现机会】单实例串行模型可以补充一个"不违反既有约束"的并发读场景

19.1节明确"单实例串行"，这个决策本身是合理的（避免过早引入细粒度锁的复杂度，17章ADR也没有把它列为需要论证的决策项，说明团队认为这是显而易见的选择）。但对于你的实际服务场景——一个Web后端要**并发响应多个用户对同一份已解析文档的只读预览请求**——"单实例串行"意味着要么每个请求重新`Open()`一次（重复解析开销），要么业务层自己在外面包锁（退化成全局串行，浪费多核）。

**建议**（不违反19.1的既有决策，是对它的补充而非否定）：可以在ADR列表新增一条候选项——提供一个显式的**只读快照句柄**（例如`Presentation.Snapshot() (*ReadOnlyView, error)`），在生成快照的瞬间做一次浅拷贝式的状态冻结，快照本身及其上的所有读方法（`Slides()`、`Shapes()`、`SpeakerNotesText()`等）保证并发安全，但快照不支持任何写操作。这不需要给`Presentation`本身引入锁，只需要在快照生成时对DocumentStore做一次revision级别的只读视图绑定即可，工程量可控，且直接服务于"服务端原生基因"（2.4节已经列为护城河之一）这条叙事——目前这条护城河的三个论据（流式加载、资源预算、单实例事务模型）都是"处理单份文档"层面的能力，缺一个"服务多个并发消费者"层面的能力，`Snapshot()`正好补上这一环。

## 三、产品创新性

2.4节已经列出的护城河和创新方向（词法保真补丁引擎、能力协商协议、动画时序IR、模板数据绑定引擎、语义Diff、有限原生预览）本身质量很高，且"立项过滤器"纪律做得很好。以下是两处在这个纪律下**仍然站得住脚、值得补充**的创新点。

### 3.1 【建议新增】WASM零上传浏览器端检查工具——直接呼应2.2节的架构红利

延续2.2节的WASM可编译性，这里有一个具体的产品化机会：把`cmd/pptx`里已有的`inspect`/`capability`/`validate`这几个只读命令，额外编译一份WASM版本，做成一个**完全在浏览器本地运行、PPTX文件不出用户设备**的检查工具（比如一个静态网页，用户把pptx拖进去，立刻在本地看到"能力矩阵报告""结构诊断""是否含未知/不安全内容"，全程不联网）。

这个点符合2.4节"立项过滤器"的两条标准中的至少一条——"竞争者架构性做不到的"：python-pptx完全无法运行在浏览器；office_oxide即便有WASM包，底层是Rust编译产物加一层桥接，产物体积和加载路径都比纯Go原生WASM更重。这不是一个同质化的"锦上添花"功能，而是"纯Go"这个已经存在的架构选择自然延伸出的能力，几乎不需要额外核心代码改动，只需要CLI层做一次编译目标适配。

对隐私敏感场景（企业合同/内部培训材料上传前想先自查是否有敏感的未知扩展内容）这个价值也是实打实的——"文件不出本地"本身就是一个可以写进产品宣传的卖点，而不是纯技术噱头。

**建议归属**：作为2.4节"护城河"表的第四项，或者作为M7创新阶段里"能力manifest工具链（TOOL-01）"的自然延伸交付物，成本很低但差异化故事很完整。

### 3.2 【建议讨论】讲稿标记语法——一个需要谨慎评估边界的创新点

这一条我要谨慎地提出来，因为它跟文档现有的ADR 009（"渲染、TTS、AI、Excel数据源适配独立，保持Go PPTX组件职责清晰"）存在张力，需要你和团队明确判断是否值得例外。

第22章已经把"自动讲解产品接入流程"作为文档明确覆盖的业务场景（而不只是"通用PPT库"的旁白），流程里第2步提到"讲稿"的准备完全交给业务层，SDK只提供`SetSpeakerNotes`/`SpeakerNotes`这类纯文本/富文本接口。这个边界本身是自洽的——ADR 009的理由是"保持职责清晰"，值得尊重。

但如果你的核心产品确实需要"讲稿里的停顿/强调标记"这类半结构化信息（这是本项目最早的产品需求之一），有一个**不违反ADR 009的折中方案**：在`ir`或一个全新的可选子包（比如`narration`）里，提供一个**纯粶析工具**——定义一套文档化的标记约定（例如`[[pause:1s]]`、`[[emphasis]]...[[/emphasis]]`），加上"解析`TextFrame`得到分段结构"和"分段结构转SSML片段"两个纯函数式的辅助方法。这个子包不属于核心PPTX读写能力，不违反"核心不import可选子包"的分层原则（第3章），也不会让SDK变成"讲稿DSL引擎"，只是给"讲解PPT"这个已经被写进第22章的目标场景，提供一个可选的、独立可测试的小工具，性质上和`render`/`ir`这些可选子包是一样的定位。

**建议**：把这个作为一条需要团队讨论的候选项列出，而不是直接要求采纳——如果团队认为"连这个也不该进SDK，应该完全留给业务层自己实现"，那也是一个自洽的立场，取决于你们对"通用库"边界的产品判断。

## 四、功能完整性

### 4.1 【发现问题，建议优先修复】缺少文档级元数据（docProps）读写能力

这是本次评审里**证据最直接的功能缺口**：2.1节把"根据模板批量生成报告、方案和培训材料"列为第一核心场景，但全文没有任何一处提到`docProps/core.xml`（标题、作者、公司、创建时间等标准属性）、`docProps/app.xml`（应用程序统计信息）或`docProps/custom.xml`（自定义属性）的读写接口。对"批量生成报告"这个场景来说，"生成的报告文档标题/作者字段是什么"几乎是一个必然需求（比如批量生成100份培训材料，每份的文档标题需要对应课程名称），但目前的公共接口目录（20章）完全没有覆盖这块。

**建议**：在5章或20章补充一组最小的文档属性API：

```go
func (p *Presentation) CoreProperties() (*CoreProperties, error)
func (p *Presentation) SetCoreProperties(props CorePropertiesPatch) error
```

复用已经确立的`Optional[T]`patch语义（5.1节），保持与`FontStyle`等其他patch类型一致的设计风格，工作量不大，但填补了一个对着核心场景#1直接相关的空白。

### 4.2 【发现问题】缺少无障碍（可访问性）元数据支持

图片、形状的替代文本（`a:cNvPr`的`descr`属性，对应PowerPoint里"编辑替换文字"功能，也是WCAG可访问性合规的基本要求）在`PictureSpec`/`AutoShapeSpec`（8章、20.2节）里完全没有出现。对于面向企业客户的产品（前文提到的审计/合规叙事，2.4节"语义Diff与审计"已经在向这个方向努力），无障碍元数据是越来越常被合规部门要求的一项，且实现成本很低（只是多读写一个XML属性）。

**建议**：在`PictureSpec`/`AutoShapeSpec`里补充`AltText string`和`IsDecorative bool`两个字段，对应的`Shape`接口补充只读访问方法。这是一个"低成本、高确定性收益"的补充，不涉及任何架构变动。

### 4.3 【发现问题，优先级较低】演示文稿级几何属性（页面尺寸）未见于公共接口

`New()`创建的演示文稿页面尺寸从哪里来、能否自定义（16:9 vs 4:3，或自定义EMU尺寸）没有在5章或20章的公共API列表中出现。这对"根据模板批量生成报告"场景可能不是高频需求（因为大多数情况下页面尺寸继承自模板），但对"完全从`New()`空白创建"的场景，如果团队认为这条路径需要被完整支持，这里需要补一个`Presentation.SetSlideSize(w, h EMU) error`或等价接口。

**建议**：如果`New()`的目标场景确实局限于"基于内置最小合法模板"（5章原文），这条可以标注为"暂不需要"；但如果未来要支持"完全自定义空白文档创建"，需要提前在能力矩阵里补一行，避免后续发现遗漏。

## 五、结论与行动建议

| 维度 | 发现 | 优先级 | 建议行动 |
|---|---|---|---|
| 逻辑合理性 | 能力矩阵(2.3)与工作包backlog(24章)之间约15项M6特性缺乏可追溯映射 | **P1** | 补充对应工作包，或在矩阵末尾显式声明backlog分解将延后进行 |
| 逻辑合理性 | 验收用例的高精确度与"不表示已实现"的免责声明存在语气落差 | P2 | 15章开头补充"设计态/验证态"区分说明 |
| 架构先进性 | 纯Go+零cgo的WASM可编译性未被验证和利用 | **P1** | 26章CI新增`GOOS=js GOARCH=wasm`编译验证项 |
| 架构先进性 | 单实例串行模型缺少面向并发只读消费场景的补充能力 | P2 | 评估新增`Snapshot()`只读并发视图，作为ADR候选项讨论 |
| 产品创新性 | WASM零上传浏览器端检查工具，是2.2节架构红利的自然产品化延伸 | **P1** | 作为2.4节护城河第四项或TOOL-01的延伸交付物立项 |
| 产品创新性 | 讲稿标记语法子包，与ADR 009存在边界张力 | P2（需团队讨论） | 作为可选`narration`子包候选方案提交团队评估，而非直接采纳 |
| 功能完整性 | 缺少文档级元数据（docProps）读写，直接对应核心场景#1 | **P0** | 补充`CoreProperties`/`SetCoreProperties`最小接口 |
| 功能完整性 | 缺少无障碍替代文本（AltText）支持 | **P1** | `PictureSpec`/`AutoShapeSpec`补充`AltText`/`IsDecorative`字段 |
| 功能完整性 | 演示文稿级页面尺寸设置接口缺失 | P2 | 视`New()`场景范围决定是否补充 |

**一句话总结**：V2.5在架构严谨性上已经是一份可以直接指导开发的高质量文档，本次评审没有发现颠覆性问题；真正值得动工前处理的是**功能完整性的P0项（docProps缺失，直接命中你自己写的核心场景#1）**，以及**能力矩阵与工作包backlog的可追溯性缺口（P1，关系到M6阶段是否会变成"写了但没人认领"的空头支票）**；WASM相关的两条建议是"低成本、高故事性"的加分项，值得纳入但不阻塞开发启动。
