## 通用教训（写入 MEMORY 候选）

- **依赖审计必须在代码 commit 前做**：r0 草案列出"36 函数不反向依赖
  根包"是凭直觉，实际大量接收根包类型。按 ADR-016 "纯实现抽取"判定

### 2. ADR-018 Tier 1 对小档语料反向劣化 10×（端到端验收才抓得到）
微基准（少而大的未变媒体）显示大赢，但端到端 PERF-01 是另一回事：

| 语料 | 改前 readAll | Tier 1 首版 | 修复后（缓冲复用） |
|---|---:|---:|---:|
| 10p-text（14KB，Part 多而小） | 103.9 KB | **1.11 MB（劣化 10.7×）** | **76.5 KB（−25.0%）** |
| 50p-image | 413.3 KB | 3.94 MB（9.5×） | 181.9 KB（−46.2%） |
| 100p-media（33.9MB） | 88.60 MB | 7.95 MB | **382.4 KB（−99.6%）** |

**根因：`io.Copy` 每次调用都新分配 32 KiB 缓冲，与 Part 大小无关。** 原 `readAll`
按体积分配（小 Part 只几 KB），改成"每个 Part 一次 io.Copy"后固定开销变成
`nParts × 32 KiB`——媒体档 Part 少而大，省下的体积项远大于固定开销故大赢；
正文型 PPTX 十几个几 KB 的 Part，固定开销就是净亏损。

**修复**：`SavePlan.Write` 整轮复用同一个 32 KiB 缓冲（`io.CopyBuffer`），
固定开销 O(nParts) → O(1)。媒体档峰值堆 62.11 → **29.08 MiB**（首次低于输入包
体积 0.86×）。

### 3. 微基准盲区（本轮最值钱的方法论）
收益锚点原本只有 `1x1MiB / 4x1MiB / 3x8MiB` 三档"少而大"用例，**结构上不可能**
发现 per-item 固定开销。已补 `200x4KiB`（200 个 4 KiB Part）哨兵：无复用 7.24 MB
vs 复用 231 KB（**31×**）。**结论：任何"改造 per-item 处理"的优化，基准必须同时
覆盖「多而小」与「少而大」两种形状。**
归因方法：不只比头尾，用**中间 commit 的 worktree** 隔离（本次用 `9bfe44d`
= Tier 1 单独 commit，直接排除 chart 重构的干扰）。

### 4. 本机墙钟时间不可用于跨轮次比较
Intel Core Ultra 9 275HX 是 **P/E 混合核**，Windows 调度在两类核间漂移，同一份
代码先后两轮 `Open/100p-media` = **6.577 ms vs 1.9 ms（3.5×）**。而已写入
PERF-01 §6：**判定回归只能用 B/op / allocs 等确定性指标**（跨轮次稳定到小数点
后 2 位），墙钟只作同轮次内横向比较；需要时间结论应在同一进程内 A/B 或用
CI 的 Linux runner。之前 ADR 里"耗时 −44.7%"的结论因此作废。

### 5. 环境备注
- **`pwsh` 在本机不可用**（PowerShell 工具是 Windows PowerShell 5.1），
  但 `go` 在 bash 与 PowerShell 下均可用 → 跑 `run.ps1` 请改用 `bash run.sh`。
- `scripts/perf/run.sh` 完整跑一轮约 **5 分钟**（不是 1m36s）。

### 发现：发布硬不变量一直是人工 grep，且手工口径本身是错的
34 Stable 段 / 50 Stable 符号 / 5 Experimental / 158 type / 17 哨兵这组数字，

**更关键**：文档记的口径 `grep '^type [A-Z]'` 实测只数出 **149**，真实值 **158**——
它漏掉了分组 `type ( ... )` 声明的 9 个。也就是说**手工口径本来就测不准**，
不自动化迟早再错一次。

### 落地：`api_surface_test.go`（根包，随 `go test` 进 CI）
用 `go/ast` + `parser.ParseDir`（filter 排除 `_test.go`）解析根包，AST 口径与文档
完全吻合（158/34/50/5/17），并把**完整名单**固化为 golden：

| 测试 | 内容 |
|---|---|
| `TestAPIFrozenCounts` | 5 项计数 |
| `TestAPIFrozenExportedTypes` | 158 个导出 type 名单 |
| `TestAPIFrozenStableSymbols` | 50 个 Stable 符号 |
| `TestAPIFrozenExperimentalSymbols` | 5 个 Experimental 符号 |
| `TestAPIFrozenStableMethods` | Stable type 上 **127 个导出方法**（`Type.Method`，真正的 binary-compat 表面） |
| `TestErrorSentinelsFrozen` | 17 哨兵的**错误字符串** + 包装后 `errors.Is` 可判定 + 字符串互不重复 |
| `TestNoBuildConstraintsInRootPackage` | 根包非测试文件不得带 `//go:build`/`// +build` |

失败信息区分 `removed`（破坏性）与 `added`（须过 ADR-015 §D），并明示
"改代码，不改 golden"。任何 API 表面变化在 code review 中就是 golden 的一行 diff。

### 灵敏度已验证（守门必须先证明抓得住退化）
- 新增导出 type → `added (1): [ZzProbeType]` 且计数 159≠158
- Stable 方法增删 → `removed/renamed (1)` / `added (1)` 明细
- `ErrNotFound` 字符串改一个字符 → `message = "pptx: not found!", want ...`
- 加 `//go:build linux` 空文件 → 报出文件名与约束内容

### 方法论（可复用）
1. **人工统计的不变量要自动化**——判断信号：该数字曾在文档里被修正过（说明易错）、
   且是发布硬门槛（出错代价高）。
2. **golden 清单优于只断言计数**：计数对不上时不知道是哪一项变了；名单 diff 能直接
   看出增删，且在 PR 里可见。
3. **AST 口径优于 grep**：`grep '^type [A-Z]'` 漏分组 `type ( ... )`；`go/ast` 用
   `parser.ParseDir` + `GenDecl.Specs` 才完整（反射无法枚举包级类型）。
4. **跨平台守门的隐藏前提**：AST 解析不看构建约束 → 若根包出现 `foo_windows.go`，
   守门测的就是各平台 API 的**并集**，在 Linux CI 上会拿"Windows 表面"比对真实
   Linux 表面，形同虚设。故补一条"根包禁止构建约束"断言（当前所有约束文件都是
   `_test.go` 或不在根包，是碰巧成立 → 已变成显式不变量）。
