代理做**纯勘察分析**（本轮无代码改动，待用户批准后再动）。

### 实测基线（可复现）
- 根包 `pptx` 单包：**74 个 .go / 35,597 行 / 158 导出类型 / 737 导出符号**。
- 全仓 138 个 go 文件分布：root 74 + internal/{opc 15, xmlstore 11, videoprobe 5, audioprobe 5}

- 依赖方向**干净**：root → internal/{opc,xmlstore,audio/videoprobe}，无反向依赖、无循环；
  `ir` 只被 cmd/pptx + wasm/check 引用（只读 IR 独立）；`render` 只被自己引用

  经查是**纯声明式 struct literal 数据表**（圈复杂度≈1），**不是坏味道，不予重构**。

### 结论：不建议做目录级大拆分
- Go 里**目录 = 包，包 = API 单元**。同包内拆目录必然换包 → 跨边界符号全部导出 →
  API 膨胀 + 循环风险。`net/http`/`go/types` 都是单包几十文件，**文件数是正常形态**。
- 设计 §3 的 5 个内部包（edit/style/textmap/geom/validate）**公共面必须留在根包**
  （用户调用 `pptx.FillInfo`/`pptx.Point`），拆出去只有两条路：① 改公开 API（破坏性）
  ② type alias re-export（纯搬运 + 双份文档负担）——**收益≈0**。
- 唯一有真实价值的是 `internal/edit`（变更集/冲突检测/事务提交），因为它承载不变量
  "所有修改必须经变更集与提交校验"（§3 关键约束"不维护两个可独立修改的文档真相"），
  当前靠 ADR 013 纪律维持而非编译器强制。但：拆分收益是**强制力而非正确性**，成本是
  35k 行搬迁 + 全部真实语料证据重跑，**发布前不划算** → 建议记录 ADR 择期。

### 段落设计原则（标准化三种形态）
