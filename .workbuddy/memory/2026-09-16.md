### 关键构造技巧（可复用）
- `zip.Writer.Create` 产出的条目**天然带 flags bit3**（Go 用 data descriptor 回填尺寸）→ 合成包条目全部被 Tier 2 门限拒绝 → 这**正是"不安全帧"的真实形态**，可直接用于回退路径测试。
- 反之，要产出**可 raw 直通**的帧必须用 `CreateRaw` + 显式 `CompressedSize64`/`UncompressedSize64`（Tier 2 现有测试即如此构造）。
- `zip.Writer` **无法**产出"未知 method / 置位加密位 / 声明尺寸 0"的帧 → 必须手工拼 ZIP（新增 helper `rawHdrZip`：local header + central directory + EOCD，可精确控制 method/flags/size）。
- 空 ZIP 的 EOCD 固定 22 字节 → 断言"未注册条目"必须解析 `zr.File` 计条目数，**不能**断言字节长度。
- 手工构造 `.rels` 条目时内容必须是合法关系流（用 `miniRels("")`）；乱写会被 `Load` 判 malformed。

## 配音样本制作（V2.6 §15.3 第 3 条语料缺口）——并挖出 PowerPoint 拒收缺陷
- **目标**：§15.3 第 3 条要求"配音功能必须有播放记录"，而语料 36 个 manifest 无任何 audio 标签样本 → 无从验证。
- **制作方法（已实测可用）**：用 SDK 生成（与 `scripts/gen_corpus/gold_replace.go` 同款 `//go:build ignore` 模式）——
  1. 代码**合成 WAV**（16-bit 单声道 PCM，440 Hz 正弦 + 50 ms 淡入淡出）→ `pptx.BytesMedia(wav, "audio/wav")`：完全自包含、可再分发、无外部依赖；
  2. `slide.AddAudio(ctx, src, AudioSpec{TrackKey, Role: AudioRoleNarration})`——时长由 probe 推导（WAV 可推导，MP3 亦可；推导不出且未显式给 `Duration` 会返回 `ErrDurationUnknown`）；
  3. `as.SetPlayback(PlaybackSpec{Trigger: PlaybackOnSlideEnter})`；
  4. `slide.SetAdvanceAfter(音频时长 + padding)`；
  5. `p.Save(ctx, out)`。
  - **前提**：模板必须**无动画**——`SetPlayback` 对含非纯音频 timing 的页面返回 `ErrTimingConflict`（AT-05）。`s001-text` 干净可用（ext-0024 有 16 个 timing 节点，不可用）。
  - 工具与产物都在 `.l3-output/`（gitignore，不提交）：`zz_genaudio.go`（生成器）、`zz_dumpzip.go`（ZIP/XML 取证工具，`-filter` + `-find` 窗口）。
- **产出**：`.l3-output/s001-text.narrated.pptx`——WAV 176444 B / 2.0 s；`docProps/audio.xml` 记 `durMs="2000"`；slide1.xml 含 audio `p:pic` + `p:timing` 音频节点；`p:transition advTm="2500"`。
- **关键发现（高危）**：**WPS 打开正常**（识别到 `Audio 11` 形状、`advanceTime=2.5` 生效、重存 OK），但 **PowerPoint 报 `0x80070570 文件或目录损坏`**。对照实验排除环境因素：同一台机、同一 COM 会话下，原样本 `s001-text.pptx` 与 Tier 2 产物 `s001-text.t2.pptx` 均 `OPEN=ok`，**只有配音产物失败**。
- **根因（源码已定位）**：`buildAudioPicFragment`（`audio.go:466`）产出的 `p:pic` 有**两处 OOXML schema 违反**：
  1. `<p:nvPicPr>` 缺必需的 `<p:nvPr/>`——同文件里 `p:nvSpPr` 都带 `<p:nvPr/>`，唯独音频 pic 没有；
  2. `<a:audioFile contentType="audio/wav"/>` 缺必需的 **`r:link`**，且被放在 `p:blipFill` 内——PowerPoint 的原生形态是把 `<a:audioFile r:link="rIdX"/>` 放在 **`p:nvPr`** 内，而 `a:blip` 指向封面图。
  代码注释自称"powerpoint 接受的 audio 形状表达之一"——该假设**未经真机验证**，与 ADR-024 / Tier 2 同源的教训（推理代替实测）。
- **影响**：**AUDIO-01/02 的产物在 PowerPoint 下不可用**；§15.3 第 3 条的缺口性质由"环境型（缺语料）"**修正为"真实代码缺陷"**（`docs/release-readiness-2026-09-12.md` 原判断"不是代码缺陷"被实测推翻）。WPS 宽容，故代码级测试与 WPS 验证都未暴露它。
- **顺带发现的次要缺陷**：`AudioShape.Profile()` 走 `lastProfileByMedia`（`audio.go:334` 手写内联解析）**漏读 `durMs`/`stMs`/`trigger`/`slide`**，而 `PlanTimingSync` 走 `parseAudioProfile`（完整解析）——两条路径不同步。后果：`Profile().Duration` 恒为 0（用户读不到时长），但主链路 `PlanTimingSync`/`ApplyTimingPlan` 正常（实测 `PLAN err=<nil> jumps=1`）。修法：`lastProfileByMedia` 复用 `parseAudioProfile`。
- **待办**：① 立项修 `buildAudioPicFragment`（须真机复验 + 回归守门）；② 修 `lastProfileByMedia` 重复解析；③ 样本正式入 corpus（`audio` 标签 + 可再分发合成音）需 opencode 配合；④ §15.3 第 3 条"播放记录"的最终证据仍需人工录屏或 Windows 音频会话枚举。
